* Hardware design phase: 
   The design of the robot will take inspiration from (A Portable, 3D-Printing Enabled Multi-Vehicle Platform for Robotics Research and Education), The robot will have a cylindrical design. It will have 3 wheel cut outs, 2 arch cutouts for the connected differential wheels and a 3rd rectangular cut out in the base for  a coaster wheel for stability. a motor will drive the differential front wheels. The casing to house everything will be 3D printed. The body will have an open top design with the 4 mounting points being made thicker for the micro controller. The purpose of the open top design is to allow airflow and easier access to the motor so that it can be connected to the microcontroller easier. All wired connections will be made using solder to maximise connection and reduce the likely hood of short circuit. For this project, which has the goal of designing a low cost SSL capable robot, I will not be adding a camera to the design as this is a proof of concept, however a space for a camera will be factored in to the design so that it may be added at a later date. SSL requires the robot to fit within a cylinder of diameter 18cm and a height of 15cm.  With this in mind the robots footprint will be 10cm in diameter and  have a hight of 10 cm, (uniform shapes are easier to 3rd print) these measurements will allow for a large range of micro controllers to be used. The robot will use a raspberry pi Pico, this was chosen as it has a small foot print (5.1 cm x 2.1 cd x 3,9 cm) and can run  micro-Ros, a distribution of ROS used on micro controller that can speak to a main ROS controller. The board itself is very cheap and has an eco system of raspberry pi hats that allow for external connection to be made such as a wifi hat or camera hat. The motor that will be used, which was inspired by  \citet{salem2013},  is a spur gear DC motor, this was chosen as they are easily accessible, affordable and have an internal gearing system allowing for better torch at lower rpms. As for the system that will be used as the master ROS, i will use a laptop to simulated the the master ROS service, since this project's aim is more geared towards the robots ability to complete tasks related to SSL, the master node being simulated by a laptop is not a server hindrance to the project. i will also add an accelerometer to the robot to better track velocity and acceleration to fine tune the robots speed to ensure they meet SSL standards. the accelerometer i plan to use is the # BMT 3 AXIS ACCELEROMETER MPU6050 as it has a small footprint and can easily be attached the raspberry pi Pico.

*  The Software stack will be designed around ROS and micro-Ros. A main ROS node (laptop) will publish nodes that the micro-ros (the robot) can subscribe to. This set up is possible as ROS uses a publisher-subscriber model allowing for distributed network of communication. The algorithms responsible for calculating the robots movements will live on the laptop and publish instructions on how to move to nodes that the robot can subscribe too, additionally the micro controller can publish sensor data to ad nodes that he main ROS client can subscribe to and process. The sensor data can be fed into the algorithms to identify what the next best move to make would be. The plan is to implement an overhead camera and mark the robot with a sigil so we can track the robots movement and share this data with main ROS system to implement movement algorithms \citep{multivehicle}.
* The robot is to be tested against the turtle bot available in the lab already. The turtlebot will perform a series of test to set a baseline standard. These metrics will then be set as the target metrics to meet or better for the robot i will build. Additonally if any metrics do not meet the standards of the SSL, these standards will be used as a reference in addition to the turtle bots performance. 
  tests : 
  top speed test:  run the robot over a distance of 5 meter in a straight-line to measure there top speed. (SSL rules says it can not exceed 1.5m/s) 
  stop test: Run the robot to top speed and measure how long it takes to stop fully once the halt command is sent, (SSL has a 2 second grace period)
  M test : mark out a course in the shape of an M, time how long the robot takes to complete the course, and make a note of how well it completes the course. 
  Latency test 1: measure how long it takes for the robot to act on a command from standstill. ie from stop issue a drive command and measure how long it takes for the robot to drive. 
  stop distance test: place a marker 5 m away from the robot, have the robot drive to the marker at top speed, once the robot is in line with the marker issue the halt command and measure the distance from the marker to the stationary vehicle. 
  turning radius test: attach a marker to the outer most point of the robot, ensure the marker is touching the surface, issue a 180 degree turn command, once the robot has rotated fully measure the radius of the arc that was drawn by the marker.
  consistency test: perform these test multiple times(5-10), plot the metrics on a graph and analysis how consistent they are.
